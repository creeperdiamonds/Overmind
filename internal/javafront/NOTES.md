# javafront

The native Java 26.1 front end. It connects Java players directly to the one shared game: each player is an ordinary Dragonfly `player.Player` in the world, and nothing here makes or reads a Bedrock packet.

## How it fits

- `front.go`: the TCP listener. Takes a connection through `javalogin.Accept` (the zero `Login` options mean Mojang login), limits connections still logging in (64 in all, 16 per address), and holds the name list. One name means one player across both editions: Java asks `OtherPlayerNames`, and `internal/app` refuses a Bedrock player through Dragonfly's `Allower`. Names compare without case.
- `conn.go`: one client. `conn` is the `player.Reporter` its player reports to and the `world.Viewer` that shows it the world.
- `chunk.go`: encodes one chunk straight from Dragonfly's storage.
- `blockstates.go`: the Java state of a block where it takes more than its runtime ID (water inside it, a paired chest).
- `silent.go`: the `Reporter` and `Viewer` methods with nothing to do yet. A method moves to `conn.go` when its feature is built.
- `worldstate.go`: the time of day, the weather, and the world's sounds and block breaks.

## What happens per player

Three goroutines: the writer (compression, encryption, socket), the ticker, and the reader.

- **World goroutine:** everything `conn` does as a viewer or reporter, so its world-side fields need no lock. It only ever queues packets. Past 8 MiB queued the client is dropped: the world never waits for the network. A frame that can't be written in 10 s ends the connection too.
- **Block states:** a block's Java state is the tables' state for its runtime ID, which includes the connections Dragonfly works out for Bedrock 1.26 (fences, panes, iron and copper bars, fire, chorus plants, redstone wire's sides; `java261.JavaState` translates them, as the pinned mapping predates them). Dragonfly also applies Java's dust rule (unconnected wire is a cross, wire linked one way runs on through), the same as minecraft.wiki's "Redstone Dust" (oldid=3841903). Walls, doors (each half has its facing, hinge and open), tall plants and stairs shapes (Dragonfly's corner) map exactly. Two things need more than the runtime ID: water on the second layer makes the block `waterlogged=true` if its Java counterpart has that property (otherwise the water does not show), and a paired chest becomes `type=left` or `right` from its block entity's pair (left when the partner is clockwise of its facing; GeyserMC's `DoubleChestBlockEntityTranslator`). A section with water on its second layer or a paired chest is encoded block by block; the others keep the palette fast path. The fluid count includes waterlogged blocks.
- **Block changes** wait for the end of the tick, after chunks already encoded, and are read from the chunk then (both layers and the block entity), so the last state goes out: one alone as a block update, several in a section as a section update. A chunk with over 1024 is marked dirty and sent again whole through the paced chunk path, nearest first, sharing the 4 chunks a tick and the open-batch limit with new chunks; edits to it wait in the resend.
- **Closing** sets a 2 s deadline on the socket, with a close 5 s later as a backstop (after the drain and the wait for the client), so nothing waits on a stalled client. It half-closes and reads until the client is done, since closing with unread data resets the connection and can destroy the disconnect message.
- **Each tick**, like the Bedrock session's background loop: move the `world.Loader` with the player, ask for up to 4 chunks (none if 10 batches are unacknowledged), send what arrived as one chunk batch, send the chunk centre and forget chunks past the radius when the player crosses a chunk edge (the loader has no callback for this, so it uses the loader's own distance rule), and keep-alive every 10 s with a 30 s limit.
- **The player's own tick** runs by itself as a world entity. Because it has a Reporter that is not `session.Nop`, it does what a Bedrock player does: no server gravity, the client decides where it is.
- **Moving:** absolute Java positions become `player.Move` deltas, ignored until the client confirms our last teleport. NaN, infinite or out-of-world values disconnect. A move over 10 blocks in a packet sends the client back, as vanilla does.
- **Dying:** health and food reach the client, at zero it shows the death screen, with Java's death message (`death_combat_event`, the key from minecraft-data's language file for the damage), and its respawn request calls `player.Respawn`. Watchers see a dead player fall over: the death status (3), health 0 and the dying pose, then it turns invisible as Dragonfly makes it, and comes back standing when it respawns.
- **Attacks (`combat.go`):** `attack` goes to `AttackEntity` after Java's entity reach (`rules.Java`: 3 blocks, 5 in creative, eyes to the target's box, plus 1). The damage is the Java player's own edition's: the conn is the fork's `player.AttackRules`, which `rules.Java` answers with Java's weapon damage in place of Bedrock's (effects and enchantments Dragonfly added scale in proportion) and Java's attack cooldown (charge `(t + 0.5) / T`, `T = 20 / attack speed`, damage × `0.2 + charge² × 0.8`, critical only over 0.9; minecraft.wiki's "Damage"). The cooldown starts again with each attack and each change of held slot. Bedrock players keep Dragonfly's rules (no cooldown, Bedrock's damage, Dragonfly's reach). `use_entity` goes to `UseItemOnEntity`. `arm_animation` swings the arm for everyone, unless Dragonfly has just swung it for an attack or a place (the client sends one after those too). Hurt shows as `damage_event` (Java's damage type from the registry, the attacker as its cause when known: a Java player's own attack, or what hurt a Java player, which a wrapper around its handler notes; the wrapper is put back each tick if anything replaced the handler, since the death screen comes from it too) and, to the client itself, `hurt_animation` turned towards the attacker; knockback is `entity_velocity` for entity 1. Swings, critical and enchanted hits show as `animation`, with 26.1's numbers (0, 4, 5). 26.3 renumbers that packet (minecraft.wiki Packets oldid=3868170 lists only 0 wake up, 1 critical, 2 magic critical), so moving to 26.3 means new numbers and another way to swing arms.
- **Breaking:** status 0, 1, 2 call `StartBreaking`, `AbortBreaking`, `FinishBreaking`. Positions outside chunks sent to this client are refused, since looking at one would load it. Creative clients send only status 0, and so does any client on a block it breaks within a tick (the player's own break time, haste and all), so those finish at once. Like Bedrock, the client decides when a block is done; there is no server timing check (no anti-cheat in the first release).
- **Placing and using items (`use.go`):** `block_place` goes to `UseItemOnBlock` with the face and the click point, so what is placed, its orientation (stairs, logs, slabs, doors, beds), what it replaces and what a click opens are Dragonfly's. Java's block reach applies first (`rules.Java`: 4.5 blocks, 5 in creative, from the eyes to the block's cube, plus 1 for latency). The true blocks always go out before the acknowledgement, since the client takes back its guess when acknowledged. Whenever a use is refused (a chunk it was not sent, a click point outside the block, out of reach, the off hand on what opens) or uses nothing up, the hand's slot is sent again, as the client took one for its guess. The off hand works too: Dragonfly uses the main hand only, so for the off hand `withHand` lends its item to the main hand for the use and puts what is left back, showing the hands once after. Dragonfly's off hand holds only Bedrock's off-hand items, so this launches fireworks. The client sends the off hand only after the main hand did nothing, so the off hand is never used on what opens. `use_item` turns the player to the look it carries (yaw wrapped to ±180, pitch held just inside ±90, since Dragonfly's `cube.Rotation` turns exactly 90 into -90) and calls `UseItem`: food and drink (finished by the server, since a Java client sends nothing when it is done, then put away), throwables, a bow (shot by Player Action 5, `ReleaseItem`). Buckets work as Java's do: nothing on a block but what opens, then in the air a ray from the eyes finds the first block (an empty bucket also the first fluid source) and uses the bucket on it.
- **Bedrock bridging for Java (`bridge.go`, `JavaBedrockBridging`, on by default; not vanilla for Java):** a Bedrock client places a block used on nothing against the block it stands on, sending an ordinary use-item-on-block with that block and a side face; a Java client places only on a face it aims at, but still sends `use_item`. So on `use_item` with a block in hand (main or off hand), the server places it as Bedrock would: when the look hits no block within Java's reach, the player is on the ground, and the look crosses the cell beside the block stood on (0.2 under the feet, as Java's `getOnPos`) in the player's cardinal facing by yaw, it calls `UseItemOnBlock` on that block and face, with the click point where the look meets the cell. Placement rules, survival counts and obstruction stay Dragonfly's; Java's reach applies to both blocks; a block that opens (a chest) is not bridged off unless sneaking. Repeats from a held button come no faster than Java's own 4-tick use cooldown. The client did not predict the block, so it shows a round trip late. Sources: minecraft.wiki, Tutorial:Bridging, "Simple bridging" (oldid=3871251): the block goes next to the one stood on "so long as you can't place a block normally where you're looking"; GeyserMC's `BedrockInventoryTransactionTranslator` (commit da836caf), whose scaffolding check flags exactly a face matching the player's 90° yaw sector. No source gives a pitch limit or Bedrock's own repeat rate, so looking at the cell stands in for the first and Java's cooldown for the second.
- **Player state (`state.go`):** `player_input`'s shift key drives sneaking and its jump key going down calls `Jump`; `entity_action` starts and stops sprinting, starts gliding (Dragonfly checks the elytra) and wakes. Swimming and the end of a glide are the server's, by Java's rules, since the client does not say: a sprinting player swims once its eyes are in water and stops when it stops sprinting or leaves the water; a glide ends on the ground or in water. Other players are shown with metadata from minecraft-data's indexes: shared flags (fire, crouching, sprinting, swimming, invisible, gliding), pose (dying, sleeping, fall flying, swimming, crouching, standing), a hand in use, health and skin layers; the bits and poses are minecraft.wiki's ("Entity metadata"), as minecraft-data gives only the types. The client is told its own shared flags and skin layers. Skin layers come from the client's settings (configuration and play); a Bedrock player shows all of them. Health is compared each tick, since Dragonfly tells only the player itself, so Java sees others hurt and heal. Bedrock sees all this through Dragonfly's own metadata.
- **Item entities (`entities.go`):** shown as Java's server shows them: `spawn_entity` (type `item`, with its velocity), then the item as metadata, then `entity_velocity`. Velocities are lpVec3, in blocks per tick like Dragonfly's (the encoding follows minecraft-protocol 1.68.0, since minecraft-data marks the type native). Pickups are Dragonfly's (`Player.Collect`, by its rules, for both editions); a pickup this client can see becomes `collect` with the count taken (the fork's `PickedUpAction.Count`: a full inventory takes part of a stack), its own included (entity 1), and the item entity's removal follows. A survival break drops through Dragonfly, so Java sees the drop. Metadata indexes and value types are minecraft-data's (`java261.MetadataIndex`, `MetadataType`).
- **Joining and leaving** go through `internal/app`'s hub, by `Options.Joined` (in the world, right after the player is added) and `Options.Left` (after its entity has left, which `session.Unlist` needs). The hub announces both editions in the chat, lists them in both editions' player lists and counts them for both server lists.
- **Player list:** `Front.List` and `Front.Unlist` keep the shared rows; each client gets them after Login (play), its own row first. A player seen before it is listed gets a row with its entity, which goes when the entity does unless the list holds it.
- **Saved data:** loaded from `Options.Players` (`internal/playerstore`) by account UUID before Login (play), so the client is told the saved game mode and position; a record that cannot be read is moved aside by the store and the player starts fresh, and `safeLoad` recovers from any panic. Saved on the world's goroutine when the player leaves (a snapshot; the store writes it), after the cursor goes back to the inventory, and every `SaveSeconds` by the hub. Data saved in another dimension loads there (`Options.Worlds`, given the Nether and the End by `internal/app`), and the client is told that dimension at Login. An account UUID online on Bedrock is refused here (`OtherPlayerUUID`), and Bedrock refuses one online here (`UUIDTaken`).
- **Server messages:** the player is subscribed to `chat.Global`, as a Bedrock session does. A message becomes system chat. A translation becomes system chat with Java's own key when Java has one (join and leave so far), otherwise its English text with Dragonfly's colour codes.
- **Chat:** a Java player's message is read by Java's rules (at most 256 characters, as the protocol reads it, and no section sign, control character or DEL, as vanilla refuses; either disconnects, as on vanilla) and goes to `player.Chat`. The hub cancels Dragonfly's own broadcast and shows the message to each player in its edition's format: Bedrock gets Dragonfly's `<name> message` line, Java gets `PlayerChat`, unsigned (profileless) chat of type `minecraft:chat`. Nothing is signed, so nothing can fail to verify on a server where Mojang and offline players mix; signatures, the chat session and acknowledgements a client sends are read past. Commands (`chat_command`, signed or not) go to `player.ExecuteCommand`; their output comes back as system chat, errors in red. A message with a Java form of its own (`JavaText`, /give's reply as `commands.give.success.single` or `.multiple`) is sent as that. A command that does not exist, or that the player may not run, is answered as vanilla answers it: `command.unknown.command` in red, then the command as sent and `command.context.here` (`commands.go`).
- **Command tree (`commands.go`):** `declare_commands` goes out after `Joined`, which tells `internal/give` whether the player is an operator. An operator gets vanilla's /give: literal `give` (restricted, as vanilla marks an operator's command), `targets` (`minecraft:entity`, players only), `item` (`minecraft:item_stack`, which the client completes, components too), `count` (`brigadier:integer`, at least 1); the parser numbers are minecraft-data 26.1 protocol.json's `command_node` mapper. Anyone else gets the root alone. Dragonfly's other commands are not in the tree; a Java client sends a command it does not know anyway.
- **Inventory (`inventory.go`):** window 0 is Dragonfly's inventory, armour and off hand: Java slots 5-8 armour, 9-35 the main inventory (Dragonfly 9-35), 36-44 the hotbar (Dragonfly 0-8), 45 the off hand; 1-4 are the 2x2 crafting grid, in Dragonfly's UI inventory where a Bedrock client keeps it (28-31), and 0 its result. The cursor is Dragonfly's UI slot 0, as for Bedrock, so leaving or closing the window puts it back. minecraft-data has no slot layout; the numbers are minecraft.wiki's and the stage 1 plan's. `HandleInventories` sets the slot callbacks a Bedrock session would: changes go to the client as `set_slot`, and the held item and armour to everyone viewing as equipment. A click (`window_click`) is worked out by the server by Java's rules (pick up, half, place one, swap, shift-click with armour to its slot, hotbar-key swap, throw, drop outside, creative clone) and then the whole window is sent, since the client's guess is only a guess; its hashes are read past. Dragging (mode 5: start, a packet per slot, end; left shares the cursor evenly, right puts one in each, middle a stack in each for creative) and double-click collecting (mode 6: the cursor gathers its item, part stacks first) follow minecraft.wiki's Packets page (oldid=3868170, "Click Container"). `set_creative_slot` works only in a game mode with a creative inventory, otherwise the client is corrected. Q, Ctrl+Q and F come as Player Actions 4, 3 and 6. Dragonfly's armour and off hand slots refuse what Bedrock refuses (the off hand takes only off-hand items, unlike Java's), and the window is sent back.
- **Block windows (`windows.go`):** a block Dragonfly opens for the player (chest, double chest, barrel, ender chest, shulker box, hopper, furnace, blast furnace, smoker, brewing stand, crafting table) opens as its Java menu (`open_window`, the type by `java261.MenuType`, the title Java's own translation key or the block's custom name), with the block's slots first and the player's inventory after, as minecraft.wiki's "Java Edition protocol/Inventory" (oldid=3201379) lays them out; the brewing stand's slots are reordered (Java has the bottles first, Dragonfly the ingredient). Clicks go through the same engine as window 0, by the window's slot map, and shift-clicks move as Java's menus do (block to inventory from the hotbar's end, inventory into the block, into a furnace's input if it smelts, its fuel if it burns). Others' changes come as `ViewSlotChange`, a furnace's progress as four window properties in ticks (fuel left, fuel total, progress, an item's time: 200, or 100 for blast furnaces and smokers, Dragonfly's). Nothing goes into a furnace's output and only fuel (an item with a burn time: not a water or milk bucket) or one empty bucket into its fuel slot (minecraft.wiki Furnace oldid=3823010), and taking the output gives the furnace's experience as orbs, as Dragonfly does for Bedrock. A window closes when the client closes it, when the block goes or changes kind, when the block's inventory is no longer the one shown (a chest that paired or lost its pair has a new one: checked before every click and each tick, since clicking in the old one duplicated items), when the player dies or leaves, and when the server closes it; then the block is told and the grid and cursor go back. **Crafting** is the player's own rule, so a Java player crafts by Java's recipes (`java261.Craft`: minecraft-data's shaped and shapeless recipes with cited corrections; shaped ones match anywhere and mirrored, as minecraft.wiki's "Crafting" oldid=3870665 says), the result mapped back to Dragonfly's item. A click on the result crafts once onto the cursor, a shift-click as many as the grid and the inventory's room allow, counting the room for what a craft leaves (a cell of several honey bottles gives a bottle to the inventory): a craft whose result and remainders do not all fit is not made.
- **Block entities (`blockentities.go`):** chunks carry, and block changes are followed by, the block entity of each block Java draws from one (chests, ender chests, signs, beds, banners, skulls, shulker boxes, furnaces, barrels, hoppers, brewing stands, beacons, lecterns, campfires, enchanting tables, jukeboxes, decorated pots, end portals), by `java261.BlockEntityType`'s IDs. A sign carries its text: `is_waxed`, and `front_text` and `back_text` with `has_glowing_text`, a dye colour and four plain-string messages (minecraft.wiki "Sign" oldid=3849680; the inner tags as prismarine-block 1.23.0 writes them). **Signs both ways:** Dragonfly's `OpenSign` becomes `open_sign_entity`; the client's `update_sign` is taken only for the side the server opened, for a sign in Java's reach, and only while that block is unchanged since the open (broken, replaced or edited by another, the open ends), characters Java does not let a player type are dropped, and the lines go to `Player.EditSign`, so Dragonfly's rules and handler apply.
- **Skins (`skins.go`):** a Java player joins with the stand-in on its profile's model and gets its Mojang skin when the fetch is done: the login's textures property names the PNG (`textures.SKIN.url`, `metadata.model` slim; minecraft.wiki "Mojang API" oldid=3782642), fetched over HTTPS from textures.minecraft.net only, redirects too (64 KB at most, 5 s), kept in memory (128 skins, about 2 MB, oldest dropped first, one fetch per skin at a time), and set with `Player.SetSkin`, so Dragonfly shows it to Bedrock: 64x64 RGBA (a legacy 64x32 skin is made 64x64, its left arm and leg the right ones, as Bedrock's built-in models are 64x64) on Bedrock's built-in `geometry.humanoid.custom` or `customSlim` (gophertunnel 1.63.0's skin files). Java players see each other's signed Mojang textures, as before. `Options.FetchSkin` replaces the fetch in tests. The stand-in is `skins.StandIn`.
- **Bedrock skins for Java (`bedrockskins.go`, `internal/skins`):** Bedrock viewers get a Bedrock skin as the client sent it (Dragonfly passes on the image, geometry, resource patch, animations and cape untouched). A Java client draws another player only in a textures property Mojang signed, hosted on textures.minecraft.net, or in one of its 18 default skins, which it picks from the player's UUID (`DefaultPlayerSkin.get`: `DEFAULT_SKINS[Math.floorMod(uuid.hashCode(), 18)]`, the nine slim then the nine wide, alex, ari, efe, kai, makena, noor, steve, sunny, zuri; 26.1.2 client decompiled at github.com/ma4z-sys/Minecraft-26.1.2). So Java clients know a Bedrock player by a UUID of its own, its row and its entity alike (`skins.ViewUUID`: the first SHA-256 of the account and a counter that, made a version 8 UUID, picks the wanted default; the same for the same account and skin every session; version 8, so never a Mojang (v4) or offline (v3) account; never a Java player online's). `skins.Classify` sorts the skin:
  - **classic**: the standard model (every base part's cube exactly gophertunnel 1.63.0's `skin_geometry.json`, wide or slim, unrotated; second-layer bones standard or absent, an absent one cleared in the image) with a 64x64 image, or 64x32 made 64x64;
  - **classic with extras**: the same with more on top (bones or cubes the standard model has not, an animated face, animations, a cape): Java gets the base image on the standard model;
  - **persona** (the client's persona flag) and **custom geometry** (anything else, or an image of another size): Java gets Steve (wide) or Alex (slim), the arm width from the model (3-pixel arms are slim; Dragonfly keeps no arm size).
  Then, by tier: (a) a classic image whose hash (SHA-256 of its 64x64 RGBA, transparent pixels zeroed) is a default skin's on the same model gets the UUID for that very default; no upload. The 18 hashes were computed outside the repo from the 26.1.2 client jar's PNGs; Bedrock's nine default skins (its vanilla skin pack, each on its own model) have exactly the pixels of Java's of the same name and model, so a Bedrock Steve, Alex, Ari, Efe, Kai, Makena, Noor, Sunny or Zuri is drawn by Java from its own copy. No image is shipped. (b) Another classic image, when an uploader is set up (below), is uploaded once and the signed textures go in the row; until then, and if it fails, (c) Steve or Alex by the UUID. Our stand-in (an odd shape replaced) is shown as Steve or Alex too. When a Bedrock player's look changes (a skin change, an upload done), every Java client's row is replaced (removed, added) and clients that see the player get it spawned again with the same entity ID, its metadata and equipment, since a Java client reads a player's skin from its row when the entity appears.
- **Odd shapes (`skins.blockOddShapes`, off by default):** when on, a Bedrock skin whose geometry goes beyond the standard player model becomes our stand-in for everyone, Bedrock viewers included, at join (the fork's `server.Config.JoinSkin`, before anyone is shown it) and on each skin change (the hub's `HandleSkinChange`). The bounds are the standard model's own: every cube, inflate included, lies in x ±8.25, y -0.25 to 32.5, z ±4.5 pixels. Odd means, with every bone and cube turned by its rotation about its pivot: anything past those bounds by more than a pixel (bigger: wings, big hats, a raised head); everything within less than half the standard height or width (much smaller); less than half of a base part (head, body, an arm, a leg) covered by anything drawn (hidden parts); something not touching the rest within half a pixel (floating parts); or a geometry that cannot be found. The standard models, named without data, are never odd. Checked on real geometry: gophertunnel's classic skin data, Bedrock's vanilla skin pack, GeyserMC's skull geometries (odd: a bigger head, a head alone) and Bedrock mob models (ghast, bat, allay, armor stand odd; zombie not), the last two kinds read from a fixtures folder outside the repo.
- **The skin uploader (`internal/skins/upload.go`), off by default:** with `skins.uploadAccount` set, a Bedrock player's classic image (the base image for one with extras) is set as the skin of that Java account through the launcher's own call (`POST api.minecraftservices.com/minecraft/profile/skins`, multipart `variant` classic or slim and `file`), then the account's signed textures property is read from `sessionserver.mojang.com/session/minecraft/profile/<id>?unsigned=false`, waiting until it names the texture just uploaded. One upload at a time, at least `uploadGapSeconds` (30) apart; a 429 waits for its `Retry-After`, else twice the last wait from 1 minute up to 30, and the skin stays first in the queue; a skin refused three times waits for the next restart. Each result is kept for good in `skins.uploadCache` (a JSON file per image hash and model, written atomically), so a skin is uploaded once ever, and the next run reads them back. A property stays valid after the account's skin changes again: it names its own texture URL.
  - **Setting up the account:** use a spare Microsoft account that owns Java Edition, not anyone's main one. Run `overmind skin-account skins/account.json`: it prints a microsoft.com/link address and a code; sign in there with that account. The file then holds a Microsoft refresh token, readable by its owner only; keep it private, it is the account. Put `uploadAccount = "skins/account.json"` under `[skins]` in `overmind.toml`. Each run swaps the refresh token for a Minecraft token by the chain prismarine-auth uses for Java (Live token with the Nintendo Switch title's client ID, Xbox user token, XSTS for `rp://api.minecraftservices.com/`, `login_with_xbox`) and writes the new refresh token back. No token is logged or put in an error.
  - **The risk:** this changes the account's skin every time a new skin needs signing. minecraft.wiki ("Mojang API") warns that many 429 answers to skin uploads can get an account suspended for a while, and automated skin changes are a grey area of Mojang's terms (MineSkin runs on donated accounts for the same reason). The pacing above keeps well under the limits for a small server, but the account can still be suspended; the server then shows Steve and Alex for new skins and keeps showing those already signed.
  - The upload and sign-in were tested against fake services only (`skintest.FakeMojang` and fakes of the Microsoft and Xbox services); nothing in the tests calls Mojang, Microsoft or Xbox Live. The real chain has not been run.
- **Dimensions (`dimensions.go`):** when the player is in another world than its loader (a portal, a respawn elsewhere, a plugin moving it through Dragonfly's API), as the Bedrock session does, the client gets a new level: Respawn with the dimension's type (its place in the dimension_type registry sent in configuration), name and sea level, data kept (attributes and metadata), then its position, inventory, health and the new world's chunks; what it was shown of the old level goes. The client makes a new level only for another dimension (26.1's `ClientPacketListener.handleRespawn` compares the dimension keys), so the old world's entities are removed and its chunks unloaded before the Respawn, or a world of the same dimension would leave them on screen. The heights and sky light are minecraft-data's (`java261.DimensionType`). The sea levels are written by hand, as no open source gives them: the Overworld 63 is minecraft.wiki's ("Terrain features" oldid=3873202: water at Y=63 and lower); the Nether 31 reads the same page's "a lava sea forms below Y=31" as its sea level; the End 0 is ours, as it has no sea (its lowest Y, nothing below sea level). Bedrock's Nether is 128 blocks tall and Java's 256, so its chunks are padded with air sections. The ticker carries on while the player is between worlds. A world calls its viewers on its own goroutine, and the world left keeps calling the conn until it has run the loader's removal from its chunks, which `Loader.ChangeWorld` queues there; so every Viewer method that touches the conn first checks `viewing` (the player is in the world the conn views, by the fork's lock-free `EntityHandle.World`, and no change is under way) and drops the call otherwise. The change itself is in two steps: `leaveWorld` stops taking callbacks, moves the loader and queues a task on the old world after the removal; once that has run, `arrive` sends the new level. The chunks sent and waiting (`ViewChunk`, which the loader calls only for its own world) have a lock of their own. While the player is in no world for a moment (a respawn), callbacks are dropped too; `showAgain` then removes the shown entities that went meanwhile and shows the entities of the chunks shown that the conn missed.
- **Other entities (`others.go`):** everything Dragonfly has besides players and items (arrows and other projectiles, falling blocks, TNT, experience orbs, fireworks, end crystals, lightning, area effect clouds, mobs when it has them) is spawned as the Java entity of its kind: the Bedrock name, else the Java entity of the same display name in minecraft-data (`java261.JavaEntityOf`; Bedrock's `xp_bottle` is named by hand as `experience_bottle`, from the pc display name "Thrown Bottle o' Enchanting"). The spawn's data is a falling block's Java block state or a projectile's owner as this client knows it (minecraft.wiki "Java Edition protocol/Object data" oldid=3328430); TNT carries its fuse and an orb its value as metadata. They move, change velocity, are picked up (`collect`) and go as any shown entity. A kind Java has no counterpart for (Dragonfly's floating text) is not shown, and logged once.
- **Respawning** in the same world sends a Respawn into the dimension the client is in, which keeps its level, chunks and entities (26.1's `handleRespawn` makes a new `ClientLevel` only for another dimension). So nothing is shown again: that gave every entity a second ID and left the first copy on screen, the ghost items a playtest found after a death. The next tick catches up on the moment the player was in no world (callbacks dropped): entities that went are removed, entities that came are shown, and the chunks are resent, nearest first. The test bot keeps its entities and chunks on such a Respawn, as the vanilla client does.
- **Items:** by `java261.JavaItem` and `BedrockItem`. Durability (Dragonfly's `max_damage` and `damage`), a custom name, lore, enchantments (by name in the enchantment registry; a curse is named the other way round), `unbreakable` and dyed leather's `dyed_color` go as components, by `java261.ComponentType`. An item Java has no counterpart for shows as a barrier named after it. From a creative client only the item, count and damage are read; other components are skipped.
- **Equipment:** `ViewEntityItems` and `ViewEntityArmour` send `entity_equipment` (0 main hand, 1 off hand, 2 boots, 3 leggings, 4 chestplate, 5 helmet: minecraft.wiki's numbers; minecraft-data gives only a byte).
- **Text** goes as NBT in modified UTF-8, which is what the game reads: NUL as two bytes and a character past U+FFFF as two three-byte halves. Plain UTF-8 there would make the client refuse an emoji. A string past NBT's 65535 bytes is cut at a character.
- **Tags** (sent in configuration by `javalogin`, `java261.Tags`) are what the client's own vanilla data refers to, so a missing tag is an empty one. What each hand-written tag drives, by minecraft.wiki's tag pages (the client runs the same code as the server for its own player where noted; which of the rest a client reads itself, rather than only a server, no open source shows, so all of vanilla's are sent):
  - **Timelines:** the client's Overworld, Nether and End dimension types name `#in_overworld`, `#in_nether` and `#in_end` as their active timelines (minecraft.wiki "Dimension type" oldid=3505985, `timelines`). A timeline drives environment attributes from the day time ("Timeline" oldid=3494697): `day` the sun, sky and light through the day, `moon` the moon phases, `early_game` the early-game attributes, and `villager_schedule` (in `#universal`, so in all three) the villagers' day. With the tag missing, no timeline runs: no day cycle and no moon phases on the client.
  - **Damage types:** `is_fire` (fire-immune entities, Fire Resistance and the `fire_damage` rule ignore it; Fire Protection reduces it), `is_freezing` (`freeze_damage` rule, 5 times for `freeze_hurts_extra_types`), `is_drowning` (`drowning_damage` rule), `is_fall` (`fall_damage` rule, Feather Falling), `is_explosion` (Blast Protection), `is_projectile` (Projectile Protection, endermen teleport, shulkers), `is_lightning`, `bypasses_armor`, `bypasses_shield` (shields do not block it), `bypasses_effects`, `bypasses_resistance`, `bypasses_enchantments`, `bypasses_invulnerability` (creative and spectator), `bypasses_cooldown`, `bypasses_wolf_armor`, `no_impact` (no velocity sync), `no_knockback`, `no_anger`, `damages_helmet`, `burn_from_stepping` (Frost Walker), `witch_resistant_to`, `wither_immune_to`, the armor stand, ender dragon, guardian and silverfish tags, `panic_causes`, `panic_environmental_causes`, `is_player_attack`, `mace_smash`, `always_most_significant_fall` (death message). Damage itself is still Dragonfly's (above); these make the client's own checks agree with vanilla.
  - **Enchantments:** `curse` (the tooltip shows the name red; a grindstone keeps it), `tooltip_order` (the order the tooltip lists enchantments in), `exclusive_set/*` (which enchantments cannot go together, which the enchantment definitions in the client's own data name), and the server-side lists `treasure`, `non_treasure`, `in_enchanting_table`, `on_random_loot`, `on_mob_spawn_equipment`, `on_traded_equipment`, `tradeable`, `double_trade_price`, `smelts_loot` and the `prevents_*` silk touch tags.
- **The world's state (`worldstate.go`, Task W):** the time of day goes as `update_time` with one clock, the Overworld's (its place in the `minecraft:world_clock` registry), its time the world's and its rate 1 while the day cycles, 0 while it stands still (minecraft.wiki "Java Edition protocol/Packets" oldid 3868170). Dragonfly sends it every 20 ticks and when the time is set, so everyone sleeping skips the night for Java too. Only the Overworld has a clock: Dragonfly's Nether and End have no time cycle. The weather goes as `game_event` when it changes: rain starting is "begin raining" (1) then the rain level (7) at 1, as the vanilla server does since those two events set the level the wrong way round; rain stopping is "end raining" (2) and level 0; thunder its level (8). A new level (join, another dimension) is sent the time and weather afresh, since the client starts it dry. Sounds both editions hear go as `sound_effect` by name (inline, so no sound IDs are needed), with the volume, pitch range and category from each sound's minecraft.wiki row: an explosion, thunder and lightning's impact (not the explosion Dragonfly also plays for a bolt), TNT lit, lava fizzing, fire put out, flint and steel, wooden and copper doors and fence gates (by wood), chests, barrels and ender chests. A block breaking goes as world event 2001 with its Java state, so the client shows its particles and plays its own break sound. Only the sounds the Java client plays itself for its own act are left out for that player, as the vanilla server leaves it out of them: its own door and fence gate, its own flint and steel (heard at the fire's block, beside the one used), and its own break. A chest, barrel or ender chest it opens is heard, since vanilla plays those to everyone and the client does not predict them. Fire and water ambience, footsteps and digging are the client's own.
- **Bad packets:** an ID not in 26.1's play table, a malformed body of a packet we read, or over 500 packets a second (burst 1000) disconnects that player and nobody else. Valid packets we do not use yet are ignored.

## What is not faithful yet

- Heightmaps: all three kinds hold the highest non-air block, so leaves count as motion blocking.
- The bucket ray treats every block as a whole cube.
- Damage to a Bedrock player from anything but a Java player's attack shows to Java as generic damage: Dragonfly does not tell viewers what hurt whom. Crawling is not worked out for Java players. Knockback follows Dragonfly (Bedrock's numbers) for everyone, as does hurt immunity.
- Other entities carry only the metadata listed above: thrown items, potions and fireworks show Java's default look for their kind (a splash potion is uncoloured), arrows are never shown stuck or critical, and an end crystal shows its base. Dragonfly has no mobs yet; when it does, they get the generic spawn and movement but no metadata of their own.
- A Java player with no Mojang skin we can fetch (offline login, no custom skin, textures.minecraft.net unreachable) shows to Bedrock in our own stand-in, drawn in code on the 64x64 layout (a skin-toned head and hands, a shirt, trousers and shoes, the overlay layer transparent), on the model its profile names: Mojang's Steve and Alex images are Mojang's, so none is shipped. Without an upload account, a Bedrock player's own classic skin shows to Java as Steve or Alex unless it is one of the default skins (above). Persona and custom-geometry skins always do: Java draws only the standard model from a 64x64 image, and flattening other geometry onto it (as GeyserMC's converter does) is not done. Capes are not carried either way. Dragonfly keeps only part of a Bedrock skin (image, geometry, resource patch's default and animated face, animations, cape, persona flag): persona pieces, their tints, arm size and skin colour are dropped before other Bedrock clients get it, upstream behaviour left alone.
- Player list rows carry the game mode at join; changes and latency are not updated.
- Game mode changes and absorption do not reach the Java client.
- A placed block makes no sound for other Java players: its sound depends on the block's sound type, which no open table gives (minecraft-data has the sound names, not each block's type). Trapdoor, shulker box and glass sounds are not sent either: their minecraft.wiki rows are in templates the tables were not read from.
- The rain and thunder levels jump to 0 or 1; the vanilla server fades them over about 100 ticks.
- Nether and End travel is not wired (no portals for Java yet); the dimension change itself works (below), and a player saved in another dimension joins there. The Nether has no block light, so it is dark to Java.
- Java players are not in `Server.Players` or Dragonfly's `PlayerCount`, so they do not fire server-wide loops. `app.Server.Online` and both server lists count both editions, and the player limit counts both through `internal/app`'s `Allow`.
- Windows Java has but this front end does not open: anvil, enchanting table, loom, grindstone, stonecutter, smithing table, beacon, lectern, cartography table. Banner patterns are not sent (only the base colour, which is in the block), nor a player head's profile. The chest lid does not open for Java watchers (block_action). Java recipes with a remainder (a milk bucket leaving its bucket) lose it; special recipes (fireworks, banner copying, dyeing, transmuting, repairs) are not done for Java. The recipe book's fill request is read past.
- A name a Bedrock player passed `Allow` with is held against Java for 15 s, even if they never arrive.
- The same Java account joining again takes over from its old session. On Bedrock, Dragonfly still refuses the newcomer.

## Known risk

A huge edit with Dragonfly's default `SetOpts` freezes the world for seconds in its redstone and neighbour-update pass (see the fork's NOTES), which stalls every connection's tick; the proof tests fill with those updates off.

## Tests

`proof_test.go` runs against a real server with `bots/java/player.js` and `bots/bedrock`. Chunks are decoded by prismarine-chunk, and minecraft-protocol parses every packet by minecraft-data's `protocol.json`; a bot's parse error fails the test. Skips if `npm install` has not been run in `bots/java`.

`bedrockskins_proof_test.go` joins Bedrock bots with real skin data (`internal/skins/skintest`: gophertunnel's classic geometry from the module cache, edited for extras, persona, custom and odd shapes; images drawn in code) and checks what a Bedrock bot and a Java bot are shown, with no uploader, with one against a fake Mojang, and with `blockOddShapes` on. Tests that need what cannot be shipped (Mojang's default skin PNGs, other projects' and Bedrock's geometry files) read them from the folder `OVERMIND_SKIN_FIXTURES` names (`java/{slim,wide}/<name>.png` from the 26.1.2 client jar, `bedrock/<name>.png` from Bedrock's `data/skin_packs/vanilla`, `geometry/*.json` and `geometry/cases.json`) and are skipped without it.
