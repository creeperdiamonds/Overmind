# worldgen

Overmind's Overworld generator. A chunk depends only on the seed, the profile and its position, so chunks can be built in any order on any number of workers. GenerateChunk keeps nothing about a chunk afterwards. Pooled scratch holds values rewritten before they are read, and caches of preliminary surface levels, walk corner columns and quart biome columns, which are pure functions of the seed and a position.

## Whose algorithms these are

**By the owner's decision, the whole generator follows Mojang's algorithms:** seeding and random numbers, noise, climate, biome lookup, splines, density, cell interpolation, noise caves, aquifers, ore veins, surface rules, carvers, ores, trees, plants and the other features below. They were written here in our own Go, in our own structure and names, from a written study of the Java 26.1 generator (`NOTES-exact-seed.md`, `NOTES-exact-features.md`). No Mojang code or file is in this repo. Numeric tables and tree-of-rules data are our own Go with their source stated.

**Where parameters came from.** The feature, placement and surface-rule values were not read from the study's data folder, which this work was told not to open. They were written from knowledge of the game and corrected against the trace and stage fixtures. The fixtures, not the writing, are the evidence.

Bedrock's biomes, heights and noise caves match Java's on the same seed (BEDROCK-NOTES section 9), so reproducing Java reaches Bedrock for those layers.

**Golden tests** compare with fixtures from a real Java server. The fixtures are not in the repo. `OVERMIND_GOLDEN` points at the first set (`golden_test.go`), `OVERMIND_GOLDEN_FEATURES` at the stage and trace set (`golden_stage_test.go`, `golden_trace_test.go`), and `OVERMIND_GOLDEN_STEP` samples every Nth chunk. Tests skip clearly if unset and fail if the folder is empty. `tools/seedcheck` compares whole worlds with Bedrock's and exits 1 under the Java figures.

Explicit `float64()` and `float32()` conversions around products stop a platform fusing a multiply-add, which would change low bits. This has run on amd64 only. `math.Sin`, `Cos`, `Log` and `Pow` are Go's; no mismatch with Java's has been seen in the traces, but neither is specified to the last bit.

**Speed without changing a result.** Some reads are skipped where a proof says the answer cannot depend on them, all in `coreAt`, `cavesAt`, `classifyCell` and `quartColumnAt`. Surface rules work out noises only when a rule reads them.

**Ties in biome lookup.** Always a cold tree search. The game keeps a per-thread last result, which decides exact ties, and a world here must not depend on which worker asked. This is the one difference left in the surface and carvers stages (about 0.04% of quarts, 1.5e-6 of blocks): with the fixtures' stored biomes in place, both stages are block-exact on all 16384 chunks.

## How a chunk is made

1. `buildBase`: noise, surface, carvers, for a chunk and for each neighbour a feature reads. Exact against Java, as above.
2. `runSource`: each of the 9 source chunks around the target is decorated **alone** against those carvers stages, by the owner's ruling. The driver follows the study's seeds and step and index order, and writes through a change log that is rolled back after the source.
3. The merge (`merger` in `generator.go`): a source's changes that land in the target are applied in row-major source order, x then z, the same order as the fixtures. Where sources overlap, the later one is treated as Java's second feature, which sees the first's blocks: it replaces a block only if it would have replaced the block it saw (same block, both base stone, both air; tree blocks over leaves and plants); a plant is refused on ground another source changed to one it would not stand on, and a write is refused if it would change the ground under another source's plant or trunk; a trunk keeps its ground, and a double plant is kept or refused whole. Each decision reads only that cell or its column, so neighbouring chunks agree on what straddles their edge.

Java itself has no single answer for step 3: two Java runs differ by 0.25 to 0.37% of blocks. See the task report for how far ours lands.

**Sources see their earlier neighbours (two levels).** In Java the chunk decorated second sees the first's blocks: its trees meet the other's canopy through the live heightmap and fail, and every random draw after them changes. So a source is not run on the bare carvers stage alone: level 0 is the source alone, and level L is the source run on top of what its earlier neighbours (before it in row-major order) do at level L-1 (`cachedLevel`). The merge uses level 2 (`sourceDepth`). It is still a pure function of the seed and position. Level 1 refused too many trees and level 0 too few. At level 2 the trees per biome match Java's (`TestPlacementRatesMatchJava`): jungle 9.59 / 9.73, roofed forest 4.58 / 4.64, bamboo jungle 2.88 / 2.75. The neighbours' blocks a source saw are their level before, so its own leaves or trunk sides can rest on a neighbour's tree that the finished world, at the next level, does not have. The tree tests allow exactly that case.

**The shared cache** (`cache.go`, ruling 26 and 31). Every worker of a generator shares one cache of carvers stages and source results (each level), pure functions of seed, profile and position, so it changes speed and never a result (`TestReuseBasesChangesNothing`, `TestSourceSameFromEitherSide`). It is capped by bytes, drops the least recently used entry first, builds each entry once when workers ask at the same time, and empties a second after the last chunk is made. Bases are kept compact (`compact.go`): a section that is all one block is one value, others a palette with a byte a cell. That is about 39 KB a base against 193 KB (`TestCompactBaseIsExact`). Workers expand a base into their own full buffer to read and write it, at most the 7 x 7 chunks a source can read.

The cap is 30 MB, the smallest at which one worker sweeps a 24 x 24 block of chunks at 35 ms a chunk or less (ruling 31): 27.8 ms, 4.6 ms wall on 16 workers, hit rate 92.7%, each base built once. At 28 MB it was 41 ms; at 24 MB and under, bases were built 6.7 times each and a chunk took 126 to 144 ms.

A source reads at most 3 chunks from itself (`sourceReach`); past that a read is air. That reach is fixed by the source and not by the chunk being made.

## Profiles

`ProfileOverjava` uses Java's algorithms and values throughout, and is what the Java golden tests run.

`ProfileBedrock`, the default, follows Bedrock Dedicated Server 1.26.60.6 where the study of it (`bedrock-study/NOTES-bedrock-exact.md`, outside the repo) has read the code, in our own Go (Task 4e, rulings 34 to 37):

- `bedrock_random.go`: Bedrock's MT19937 Random with its method semantics, the decoration chunk seed, the per-rule seed (FNV-1 of the identifier, hash_combine), and the bedrock floor from each chunk's own MT stream (R1).
- Deepslate in the noise stage under "minecraft:depth_based_layer" (R2); `bedrock_surface.go`: the default surface builder (phase 5), with the Java rules kept for the mesa, swamp and frozen ocean builders not read yet.
- `bedrock_carvers.go`: the two cave carvers and the canyon (5a, 5b, P2), instead of Java's carvers.
- `bedrock_deco.go`: decoration in BDS's parity order (Q0). A source runs on top of its lower-phase neighbours' writes, each decorated the same way, so a chunk is still a pure function of seed and position; final blocks apply the nine sources by phase, then z, then x. Rule scatter (section 3) and a run per biome of the chunk.
- `bedrock_ores.go`: OreFeature (section 4) for the underground pass's ore and rock rules, with T2's rule that a one-biome chunk does not height-test positions; `bedrock_disks.go`: the sand, gravel and clay disks (R5).
- Since Task 4e round 3 a feature interpreter (`bedrock_feat*.go`, `bedrock_trees*.go`, `bedrock_plants.go`, `bedrock_molang.go`) runs every rule of the seven passes whose feature it knows: composites, trees, plants, lush caves, kelp and seagrass, and the freeze pass. What it does not know yet (dripstone, sculk, geodes, glow lichen, coral, pale oaks, lakes, monster rooms and a few more; mangroves since Task 9 round 17 are Bedrock's) is still Java's algorithm, run among Bedrock's passes in Java's steps; `javaKeep` keeps the Java placement where a Bedrock rule is skipped.
- Since Task 4e round 5, with the data read: BDS's biome table (`bedrock_sulfur.go`, study T10, T11): Java's rows with dripstone caves' humidity below 0.7, sulfur caves before deep dark and dappled forest in some plains rows (each only when the data registers the biome), and BDS's truncated endpoints; the tree is per generator, so Overjava keeps Java's. BDS's stored 3D biomes (`bedrock_biomes.go`, T11): the table on an 8-block grid with BDS's quantization and warm searches up each sample column, a jittered nearest corner per block, and the sky sections as copies of the top real one; decoration, the surface pass's column biome and the subsurface pass read them, while the chunk's stored biomes (for the client) and Java's placements keep the quart model. The subsurface pass (T12): after the surface pass and before the carvers, each column up to its preliminary surface - 8 is cut into runs of one biome, and a run whose biome has a noise_gradient builder (sulfur caves' cinnabar and sulfur, T7) is built from one under its top. `bedrock_limits.go`: what the data may ask for (numbers, radii, weights) and a budget of scatter placements per source chunk, so broken data cannot stall a worker; feature cycles are broken data.

Bedrock's feature data (features, feature rules, biomes) is read at startup from a local Bedrock install (`BedrockDataDir`, `bedrock_pack.go`), by the owner's decision of 2026-11-04: the newest vanilla pack's copy of each file, the pass order from the study's libc++ map model, the server's definitions folder for what no pack has. In the repo are only algorithm constants: RNG, hashes, the floor and canyons, read from the code, and the code-registered features. Two of those are measured from BDS worlds, not read from the code, and are labelled so (ruling 39): the built-in dirt rule as an ore of 33 (144/144 first blobs) and the carvers' replaceable test (granite never carved, tuff and the iron vein always). Biome temperatures and the counts of the Java placements standing in for unwritten rules (underwater magma, glow lichen) come from the data when it is read; the tables in the repo are only the fallback. With no install the Bedrock profile keeps the floor and deepslate gradient and uses the built-in Java-based surface, carvers and features, which are approximate; the server logs one line saying so. Tests read the data from `OVERMIND_BEDROCK_DATA` and skip without it. `TestBedrockWorldsMatchBDS` and `TestBedrockFirstOreBlobs` compare with BDS worlds under `OVERMIND_GOLDEN_BEDROCK`; see the Task 4e report for the scores.

## Water

Carvers carve under water as the aquifer says, and the noise pass seals nothing, as the notes and fixtures have it. So generated water can hang over air. In the game it flows when a chunk first ticks; here it stays until a block update, as springs do. Lakes are lava only, as the study says the Overworld has.

## Heights

- `SurfaceHeight` is the highest block at the carvers stage that is not air or water: the terrain before any feature. It builds that one column, cutting every tunnel that reaches it through `walkCarvers` and `carverReach` with one mask. `TestSurfaceHeightMatchesCarverStage` holds it to the chunk.
- `NoiseHeight` is the noise stage's highest solid block.
